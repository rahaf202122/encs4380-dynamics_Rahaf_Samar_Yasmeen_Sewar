My system · Micromouse drive motor

A PI speed loop for one wheel of our Micromouse.

1. The plant and where its numbers come from

All motor numbers below are taken from the datasheets of our parts. Our Micromouse drives each wheel with an N20 DC gear motor with magnetic encoder, 6 V, 530 RPM (Roboticx part ROBO-18014), through an L298N driver, controlled by an ESP32, and powered by 2 × 18650 Li-ion cells. The model is the first-order plant from Module 1:

G(s) = K / (τs + 1),   input: PWM duty in %,   output: wheel speed in rpm

2. The spec and why it matters for the Micromouse

  • Damping 0.6 ≤ ζ ≤ 0.8 (we use 0.75): the practical range from the lecture, fast but without ringing.
  • Overshoot ≤ 10 %: if a wheel overshoots its speed, the mouse drifts in a turn or slips on the floor.
  • Settling time (2 %) ≤ 0.3 s: the mouse changes speed at every cell. Both wheels must reach their speed quickly, or the mouse does not drive straight.
  • Zero steady-state error: both wheels must turn at exactly the commanded speed, again so the mouse drives straight. PI control gives this.
  • PWM within 0–100 %: the L298N cannot give more than full duty, so the design must work inside this limit.
  • Target 300 rpm: about 63 % of the top speed (≈ 477 rpm), which leaves room for the controller to speed up.

3. PI design and simulated response

With PI control the closed loop is τs² + (1 + KKp)s + KKi = 0. Matching it to τ(s² + 2ζωn s + ωn²) gives Kp = (2ζωnτ − 1)/K and Ki = τωn²/K. The PI zero adds some overshoot, so the simulation (RK4, with the 0–100 % PWM limit and anti-windup) checks the real result.

Is the design safe if τ is different?

The same gains are run with τ halved and doubled. A good design should still settle in all three.

4. ESP32 code for these gains

The code updates every 10 ms: it reads the wheel speed from the encoder, computes the PI command with anti-windup, and writes the PWM to IN1 of the L298N (the ENA jumper stays on). The gains change when you move the sliders.
